## Highlights

CAIPE 1.3.5 brings platform and app feedback into one form. You can choose the
component and feature, see where the issue will be created, and include the
context you want to share. This release also restores the GitHub connection in
Docker Compose installations and updates security dependencies.

<!-- truncate -->

## What's New

### One feedback form for the platform and apps

- **Report directly from a response** — Thumbs down opens Provide Feedback
  without an intermediate reason dialog when reporting is enabled
  ([#2397](https://github.com/caipe-io/ai-platform-engineering/pull/2397)).
- **Start with the right component** — Registered apps can open the shared
  form with their component selected. Changing Component updates its feature
  choices while keeping your report text
  ([#2397](https://github.com/caipe-io/ai-platform-engineering/pull/2397)).
- **See the destination** — The form shows the configured GitHub repository
  or Jira project before you submit
  ([#2397](https://github.com/caipe-io/ai-platform-engineering/pull/2397)).
- **Describe the problem or improvement** — Choose Bug or Enhancement, add
  reproduction steps or your goal, and optionally select Blocks my work,
  Annoying, or Minor to describe the impact
  ([#2397](https://github.com/caipe-io/ai-platform-engineering/pull/2397)).
- **Choose what context to share** — Chat excerpts are optional and editable;
  configured destinations can accept screenshots
  ([#2397](https://github.com/caipe-io/ai-platform-engineering/pull/2397)).

## Bug Fixes

- **GitHub connections in Docker Compose**: the GitHub integration no longer
  starts in a mode that exits when the container runs in the background
  ([#3193](https://github.com/caipe-io/ai-platform-engineering/pull/3193)).
- **Feedback retries**: closing and reopening a failed report reuses its
  pending or saved response rating, while the ticket receives your updated
  report details
  ([#2397](https://github.com/caipe-io/ai-platform-engineering/pull/2397)).
- **Feedback destinations**: app reporting failures stay with the selected
  component instead of silently falling through to platform reporting;
  unavailable platform destinations are omitted from the picker
  ([#2397](https://github.com/caipe-io/ai-platform-engineering/pull/2397)).

## Security

Token validation and PDF processing dependencies receive security updates
([#3185](https://github.com/caipe-io/ai-platform-engineering/pull/3185),
[#3187](https://github.com/caipe-io/ai-platform-engineering/pull/3187)).

## Breaking Changes

**Existing platform feedback reporting needs an explicit handler.** Deployments
that previously relied on the Jira or GitHub agent flow must select that flow
in their configuration. Direct GitHub reporting requires its own repository
and service credential. Without these settings, platform reporting is
unavailable. Follow the migration examples below before upgrading.

instead of the intended blog. Administrators can select this post through the

## Upgrade Guide: 1.3.4 → 1.3.5

### Overview

- The published parent-chart values are unchanged. The UI subchart adds one
  optional setting, `existingSecretOptional`, with a default of `false`.
- Platform feedback configuration is an application migration even though
  those variables do not appear as new parent-chart defaults.
- Installations that already disable issue reporting can retain their current
  values. App feedback registration is optional and deployment-owned.

If you want response ratings without issue reporting, set
`caipe-ui.config.REPORT_PROBLEM_ENABLED` to `"false"`. This retains the
lightweight response-feedback dialog without requiring an issue destination.

### Helm Values Changes

| Setting | Default | Action |
|---------|---------|--------|
| `caipe-ui.existingSecretOptional` | `false` | Keep required secrets required. Use `true` only when `existingSecret` contains optional feature credentials. |
| `caipe-ui.config.FEEDBACK_HANDLER` | Unset | Set `agent` to retain the configured Jira/GitHub agent flow, or `github` for direct GitHub issue creation. |
| `caipe-ui.config.FEEDBACK_GITHUB_REPO` | Unset | Required for direct GitHub reporting, in `owner/repo` format. |
| `FEEDBACK_GITHUB_TOKEN` in the UI environment | Unset | Required for direct GitHub reporting; supply through a deployment secret. |
| `caipe-ui.config.FEEDBACK_COMPONENTS_JSON` | Unset | Optionally register GitHub handlers, features, and token references for installed apps. |
| `caipe-ui.config.FEEDBACK_FEATURES` | Built-in platform categories | Optionally replace platform feature choices with a JSON string array. |
| `caipe-ui.config.FEEDBACK_GITHUB_STYLE_JSON` | Built-in issue conventions | Optionally configure title prefixes and labels; apps can define their own `style`. |

#### Retain an existing agent-backed destination

For an existing Jira deployment, add the explicit handler while retaining its
provider settings. The same `FEEDBACK_HANDLER: agent` migration applies to an
existing GitHub agent destination with `GITHUB_TICKET_ENABLED` and
`GITHUB_TICKET_REPO` configured.

**Before (1.3.4):**

```yaml
caipe-ui:
  config:
    JIRA_TICKET_ENABLED: "true"
    JIRA_TICKET_PROJECT: EXAMPLE
```

**After (1.3.5):**

```yaml
caipe-ui:
  config:
    FEEDBACK_HANDLER: agent
    JIRA_TICKET_ENABLED: "true"
    JIRA_TICKET_PROJECT: EXAMPLE
```

Jira support remains available through the agent handler. The agent must resolve
a supported issue type for the configured project instead of treating
Enhancement as a literal Jira issue-type name. If the handler is omitted or its
provider/project is missing, the platform component cannot accept reports.

#### Use direct GitHub reporting

To move an existing GitHub agent destination to the direct handler:

**Before (1.3.4):**

```yaml
caipe-ui:
  config:
    GITHUB_TICKET_ENABLED: "true"
    GITHUB_TICKET_REPO: example/support
```

**After (1.3.5):**

```yaml
caipe-ui:
  config:
    REPORT_PROBLEM_ENABLED: "true"
    PROVIDE_FEEDBACK_ENABLED: "true"
    FEEDBACK_HANDLER: github
    FEEDBACK_GITHUB_REPO: example/support
  existingSecret: example-feedback
  existingSecretOptional: true
```

Supply `FEEDBACK_GITHUB_TOKEN` in the existing `example-feedback` Kubernetes
Secret through your deployment's secret manager. It needs permission to create
issues in the destination repository. Legacy GitHub repository and token
settings are not fallbacks for the direct handler; missing dedicated settings
disable that destination. Keep credentials out of `values.yaml` and component
registration JSON.

`REPORT_PROBLEM_ENABLED` controls reporting; `PROVIDE_FEEDBACK_ENABLED` enables
the optional platform header entry point. Screenshots additionally require
`FEEDBACK_GITHUB_SCREENSHOTS_REPO` and permission to write files there.

#### Register app feedback when needed

For each installed app using a host-managed GitHub handler, configure its
repository, features, and a dedicated `FEEDBACK_*_TOKEN` environment reference
in `FEEDBACK_COMPONENTS_JSON`. The registration does not install an app.
Native and iframe app entry points must adopt the shared feedback capability.
Existing app-owned `feedback_path` handlers remain supported and require a
runtime origin. See the
[feedback configuration](https://github.com/caipe-io/ai-platform-engineering/blob/1.3.5/ui/README.md#app-feedback)
and [app SDK](https://github.com/caipe-io/ai-platform-engineering/blob/1.3.5/ui/app-sdk/README.md#shared-feedback-form)
for the complete contracts and examples.

### Upgrade Runbook

1. **Apply the feedback configuration above** if platform reporting is in use.
   Provision the referenced secrets before enabling the destination.
2. **Upgrade the chart** using your existing release name, namespace, and values:

   ```bash
   helm upgrade example \
     oci://ghcr.io/caipe-io/charts/ai-platform-engineering \
     --version 1.3.5 \
     --namespace example \
     -f your-values.yaml \
     --wait --timeout 10m
   ```

   Replace `example` with your existing release and namespace. Update any
   separately pinned image tags to the intended release images as well. The
   dependency refresh includes `joserfc` 1.7.6 in affected MCP/RAG services,
   `pyasn1` 0.6.5, and `pypdf` 6.21.4 in affected ingestion/RAG components.
3. **Verify workload health and feedback**:

   ```bash
   kubectl get pods -n example
   kubectl get events -n example --sort-by=.lastTimestamp
   ```

   Check sign-in and chat streaming. Open feedback from the platform and a
   registered app; confirm the selected component, feature list, and repository
   or project. Cancel without submitting, then use an authorized test report
   if you need to verify actual issue creation. For Jira, verify a supported
   issue type in the destination project.
4. **For Docker Compose GitHub users**, apply the updated Compose definition
   and recreate `github-mcp-server`. It now runs `http --port 8082`, with the
   existing host mapping `18000:8082`. Verify its HTTP MCP connection after
   recreation.

### Deployment Impact

No deployment-specific values were supplied for this release post. The
required action is to configure a handler for any existing platform feedback
flow. Optional app registrations and issue conventions can be adopted
independently.
