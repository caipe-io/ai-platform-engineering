## Highlights

CAIPE 1.3.2 makes Webex conversations easier to follow. Replies show the selected
agent's friendly name and, in group spaces, the correct bot to mention next.
Long answers fit within message limits while preserving a link to the complete
response when it can be saved and opened in the web UI.

<!-- truncate -->

## Bug Fixes

- **Clearer reply labels** — Webex replies show the agent's friendly name instead
  of its internal ID. Group replies identify the receiving bot to mention;
  direct messages omit the unnecessary mention prompt. Replies continue even
  if the agent's name cannot be loaded
  ([#2979](https://github.com/caipe-io/ai-platform-engineering/pull/2979)).
- **Reliable long replies** — Oversized answers keep their original opening
  text and, when available, link to the full response. The bot continues working
  after preview updates stop and can post a final reply in the same thread when
  an edit is rejected
  ([#3046](https://github.com/caipe-io/ai-platform-engineering/pull/3046)).
- **Complete responses in the browser** — New successful Webex turns save the
  full question and answer before publishing a continuation link. Opening that
  link retains normal sign-in and conversation-access checks
  ([#3046](https://github.com/caipe-io/ai-platform-engineering/pull/3046)).

## Breaking Changes

No Helm configuration keys were added, removed or renamed in this release. No database migration is required for these fixes.

## Known Issues and Limitations

- Older Webex turns that stored only conversation metadata are not backfilled
  with full message text.
- If saving the response fails or a public browser URL is unavailable, the
  reply reports that the full-response link is unavailable.
- A link posted in a Webex space does not grant other participants access to
  the conversation. Existing sign-in and access requirements still apply.
- Live Webex delivery and signed-in browser viewing remain rollout checks;
  the merged fixes were validated with automated tests.

## Upgrade Guide: 1.3.1 → 1.3.2

### Overview

The application changes are confined to the Webex bot. Deploy the 1.3.2 bot image
for the fixes to take effect. Existing Helm values remain valid; full-response
links need a public browser URL in the bot's configuration.

### Helm Values Changes

The published parent-chart values are identical between 1.3.1 and 1.3.2.
There are no required values edits for the upgrade. Chart metadata and dependency
versions advance to 1.3.2; the chart reports `appVersion: 1.3.2`.

The bot accepts these settings through the existing `webex-bot.config` map:

| Setting | Default / fallback | Operator action |
| --- | --- | --- |
| `CAIPE_UI_BASE_URL` | Unset | Set the public browser origin for full-response links. |
| `WEBEX_LINKING_BASE_URL` | Used when `CAIPE_UI_BASE_URL` is empty | Keep an existing public URL, or set the preferred setting above. |
| `WEBEX_MESSAGE_MAX_EDITS` | `10` | Keep the default unless a different limit is confirmed; accepted values are 1–20. |
| `APP_NAME` | Chart default `CAIPE` | Keep the deployment's existing display name for link labels and fallback bot labels. |

These are runtime configuration options, not new chart schema fields. Values
outside the supported edit-budget range stop the bot at startup. No new Vault
paths, secret keys, or bot-token rotation are required.

### Upgrade Runbook

#### 1. Configure the public browser URL

Merge the following into existing values if neither public URL setting is
already configured:

```yaml
webex-bot:
  config:
    CAIPE_UI_BASE_URL: "https://chat.example.com"
    WEBEX_MESSAGE_MAX_EDITS: "10"
```

Use the browser-accessible URL, rather than an internal API service address.
Existing bot identities, tokens, routes and access policies can remain unchanged.

#### 2. Upgrade the chart

```bash
helm show chart oci://ghcr.io/caipe-io/charts/ai-platform-engineering --version 1.3.2
helm upgrade example oci://ghcr.io/caipe-io/charts/ai-platform-engineering \
  --version 1.3.2 \
  --namespace example \
  -f your-values.yaml \
  --wait --timeout 10m
```

Use your actual release name and namespace. For GitOps, update the chart version
in the deployment repository and let the controller reconcile it. Update any
explicit Webex bot image tag/digest override as well; an old override prevents
the new bot code from being deployed. Keep Webex disabled in installations that
do not use it.

#### 3. Verify Webex and browser behavior

```bash
kubectl get pods -n example
```

- In a group space, confirm the footer identifies the selected agent and the
  receiving bot. In a direct message, confirm it omits the mention prompt.
- Request a long answer and confirm the preview stops updating without stopping
  the answer. Follow its full-response link while signed in as the conversation
  owner and check that the complete question and answer are present.
- Confirm another user still needs the appropriate conversation access; the
  continuation link must not create a public share.
- Verify a normal short answer and continuation in the same Webex thread.

Replies are capped at 7,439 UTF-8 bytes including the footer. Preview updates
require both 240 new characters and a one-second interval, and reserve one edit
for completion or errors. Truncation does not make an additional model call or
summarize the answer.

### Deployment Impact

- **Without Webex:** no integration configuration changes are needed for these fixes.
- **With Webex:** deploy the new bot image, check the public URL and edit budget,
  and validate a long response in both Webex and the browser.
- Review any deployment-specific overrides against the settings above; these
  notes do not establish the live state of a particular environment.
