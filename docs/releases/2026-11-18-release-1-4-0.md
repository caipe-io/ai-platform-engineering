## Highlights

CAIPE 1.4.0 brings a unified place to create and connect agents, guided setup,
and model connections you can save and test. A major architecture change adds
Harness Engine for durable conversations across supported runtimes: configured
agents can keep working through a browser reconnect while existing conversations
retain their selected runtime. The release also strengthens access revocation,
fixes Slack approvals, and improves hosted apps and Webex meeting retrieval.

## What's New

### A major step in agent execution

- **Conversations that survive reconnects** — Harness-enabled agents keep their execution separate from the browser connection, allowing chat to reconnect and recover saved progress without resending the prompt.
- **More runtime choices** — Configure Claude Agent SDK, remote SDK and ACP workers, Claude Code, or Amazon Bedrock AgentCore alongside Deep Agents; existing chats keep their published agent version and runtime ([#3190](https://github.com/caipe-io/ai-platform-engineering/pull/3190), [#3238](https://github.com/caipe-io/ai-platform-engineering/pull/3238)).
- **Delegate to the configured specialist** — Deep Agents supervisors can call supported Harness-owned subagents using the child's saved runtime and profile, with a separate child session and the caller's permissions ([#3390](https://github.com/caipe-io/ai-platform-engineering/pull/3390)).
- **Manage runtime profiles** — Administrators can publish named Claude profiles with a model and default turn limit; authors select a profile when building an agent ([#3386](https://github.com/caipe-io/ai-platform-engineering/pull/3386)).
- **Evidence-based research profiles** — Optional Claude Code research profiles check investigation and challenge evidence before presenting a completed report ([#3395](https://github.com/caipe-io/ai-platform-engineering/pull/3395)).

Deep Agents retains its existing execution path unless an operator enables the
Engine integration. Other runtime integrations are **experimental** and require
operator configuration. Please report regressions in existing chat, history,
sharing, approvals, or tool behavior when enabling the new architecture.

### One place to create, connect, and discover agents

- **One Add agent flow** — Choose **Create in CAIPE** or **Connect existing** from the same agent catalog ([#3422](https://github.com/caipe-io/ai-platform-engineering/pull/3422)).
- **A clearer catalog** — Browse cards, search, filter by runtime, and inspect connection details for created and connected agents ([#3401](https://github.com/caipe-io/ai-platform-engineering/pull/3401), [#3403](https://github.com/caipe-io/ai-platform-engineering/pull/3403)).
- **Discover before connecting** — Review Agent Cards from supplied URLs or an operator-enabled Kubernetes discovery source before registering an A2A agent ([#3384](https://github.com/caipe-io/ai-platform-engineering/pull/3384)).
- **Choose subagents together** — Select supported CAIPE agents, configured ACP agents, and registered A2A specialists in one builder picker ([#3391](https://github.com/caipe-io/ai-platform-engineering/pull/3391)).

A2A connection tests inspect the Agent Card; they do not run a task. Registered
A2A agents remain available through supervisor delegation. **Direct standalone
A2A chat and Agent Teams are outside this release**; configured ACP agents retain
their existing direct-chat path.

### Easier setup, model connections, and skills

- **Guided first-agent setup** — Administrators choose a model, create a starter agent, optionally attach context, and verify a real reply; users can replay the CAIPE product tours ([#2763](https://github.com/caipe-io/ai-platform-engineering/pull/2763)).
- **Save and test model providers** — Create named connections, reuse saved credentials, register model IDs, and test a completion before or after saving ([#3389](https://github.com/caipe-io/ai-platform-engineering/pull/3389)).
- **Import original skill packages** — Import upstream entry files and supporting content at a fixed GitHub revision, with package scanning and revision checks before runtime use ([#3249](https://github.com/caipe-io/ai-platform-engineering/pull/3249)).
- **Broader FinOps context** — Optional Cloudability integration adds cloud-cost reporting alongside existing model-spend tools and configurable token-usage alerts ([#2019](https://github.com/caipe-io/ai-platform-engineering/pull/2019)).

### Hosted apps and team channels

The **CAIPE Agentic App v2 experience** hosts external apps within CAIPE.
An app can present its UI in an iframe while its assistant runs in a separate
service. The app continues to own its data and assistant configuration; the
host supplies the shared navigation and conversation experience. Installing or
upgrading CAIPE does not itself migrate an external app's stored data.

- **Keep your place in an app** — Hosted apps preserve their URLs and scroll independently within the host ([#3257](https://github.com/caipe-io/ai-platform-engineering/pull/3257)).
- **Shared assistant choices** — Apps can use shared platform assistants and expose optional checkbox choices in the shared composer ([#3189](https://github.com/caipe-io/ai-platform-engineering/pull/3189), [#3134](https://github.com/caipe-io/ai-platform-engineering/pull/3134)).
- **Optional durable bot conversations** — Slack and Webex can use Harness Gateway for supported Engine agents, including reconnect and replay while the bot process is running ([#3241](https://github.com/caipe-io/ai-platform-engineering/pull/3241)).

## Bug Fixes

- **Shared-chat access**: removing a person's shared access now persists the revocation; permanently deleting a conversation cleans up its grants ([#2326](https://github.com/caipe-io/ai-platform-engineering/pull/2326)).
- **Sharing actions**: sharing updates that contain no metadata changes no longer attempt an invalid database update ([#3425](https://github.com/caipe-io/ai-platform-engineering/pull/3425)).
- **Former administrators**: a new login or refreshed-claim check removes recorded login-derived administrator access when the configured admin group is absent; independent manual and bootstrap access is preserved ([#2197](https://github.com/caipe-io/ai-platform-engineering/pull/2197)).
- **Manual administrator grants**: login demotion no longer removes a separately recorded manual grant or restores a revoked manual reason; uncertain new grants are held for operator review ([#3427](https://github.com/caipe-io/ai-platform-engineering/pull/3427)).
- **Missing names**: bootstrap-created user profiles can acquire missing first and last names from later SSO sign-ins without overwriting existing names ([#3421](https://github.com/caipe-io/ai-platform-engineering/pull/3421)).
- **Slack approvals and forms**: resume requests now send the field expected by the chat service, fixing the reported missing-resume-data error ([#3430](https://github.com/caipe-io/ai-platform-engineering/pull/3430)).
- **External-app upgrades**: an empty starter catalog no longer hides an existing catalog supplied through a custom file or directory mount ([#3415](https://github.com/caipe-io/ai-platform-engineering/pull/3415)).
- **Chat recovery**: saved turn anchors and shared-tab discovery improve recovery of Harness conversations after a refresh or another participant's turn ([#3368](https://github.com/caipe-io/ai-platform-engineering/pull/3368), [#3376](https://github.com/caipe-io/ai-platform-engineering/pull/3376)).
- **Unavailable tools**: starting a Harness chat now checks tool availability before admission, and missing optional caller connections are handled more reliably ([#3392](https://github.com/caipe-io/ai-platform-engineering/pull/3392), [#3374](https://github.com/caipe-io/ai-platform-engineering/pull/3374)).
- **Webex meetings**: completed meetings and shared recaps are easier to find, with bounded parallel lookups and resumable results ([#3371](https://github.com/caipe-io/ai-platform-engineering/pull/3371)).
- **Webex transcripts**: recurring-meeting lookups verify the requested occurrence instead of falling back to an older meeting with a similar title ([#3242](https://github.com/caipe-io/ai-platform-engineering/pull/3242)).
- **Webex linking**: account-linking completion and incomplete space-route recovery provide clearer next steps ([#3146](https://github.com/caipe-io/ai-platform-engineering/pull/3146), [#3243](https://github.com/caipe-io/ai-platform-engineering/pull/3243)).
- **Slack ingestion retries**: a failed ingestion submission no longer advances the channel checkpoint; asynchronous server-side processing failures remain a known limitation ([#3363](https://github.com/caipe-io/ai-platform-engineering/pull/3363)).
- **Model and builder settings**: publication preserves native model controls, tool selection is explicit, and agent creation requires an owner choice ([#3253](https://github.com/caipe-io/ai-platform-engineering/pull/3253), [#3394](https://github.com/caipe-io/ai-platform-engineering/pull/3394), [#3362](https://github.com/caipe-io/ai-platform-engineering/pull/3362)).
- **Sign-in and navigation**: login retries preserve the protected destination, chat counts follow the live picker, and the header again opens active chat navigation ([#3269](https://github.com/caipe-io/ai-platform-engineering/pull/3269), [#3370](https://github.com/caipe-io/ai-platform-engineering/pull/3370), [#3247](https://github.com/caipe-io/ai-platform-engineering/pull/3247)).
- **Feedback and tracing**: conversation feedback and user attribution now attach to the corresponding Langfuse session and observations ([#3429](https://github.com/caipe-io/ai-platform-engineering/pull/3429)).

## Security and Compatibility

- Claude Code remote sessions use restricted isolation by default; operator configuration and supported hosts are required ([#3377](https://github.com/caipe-io/ai-platform-engineering/pull/3377), [#3383](https://github.com/caipe-io/ai-platform-engineering/pull/3383)).
- Browser diagnostics no longer log complete API response bodies ([#3410](https://github.com/caipe-io/ai-platform-engineering/pull/3410)).
- Credential rotation and revoked access are rechecked when cached model connections are reused ([#3389](https://github.com/caipe-io/ai-platform-engineering/pull/3389)).
- Dependency fixes and stricter OIDC refresh validation are included; this is not a claim that every release image is vulnerability-free ([#3314](https://github.com/caipe-io/ai-platform-engineering/pull/3314), [#3355](https://github.com/caipe-io/ai-platform-engineering/pull/3355), [#3255](https://github.com/caipe-io/ai-platform-engineering/pull/3255)).

## Upgrade Requirements

Existing conversations keep their runtime bindings. Enabling Engine routing does
not automatically move legacy conversations, and existing chats do not switch
runtime when an agent is edited. Operators must review the authorization,
identity-provider, and optional-runtime changes below before upgrading.

## Known Issues and Acceptance Still Required

- **Slack ingestion**: a checkpoint can still advance before asynchronous server-side processing finishes, potentially skipping a message that later fails processing ([#3364](https://github.com/caipe-io/ai-platform-engineering/issues/3364)).
- **Bot reconnects**: opt-in Harness transport has no persisted delivery outbox or automatic catch-up after a bot process restart. Platform redelivery can replay text into another reply.
- **Delegated approvals**: Harness child delegation is bounded and synchronous; parent-driven approval/resume of a paused child and automatic failed-parent recovery are not provided.
- **First-use availability**: with Engine configured, an unbound chat may require an Engine lookup even when legacy Deep Agents routing remains selected; an outage can therefore block that first-use path ([#3223](https://github.com/caipe-io/ai-platform-engineering/issues/3223)).
- **Release acceptance**: the rc.8 source contains the admin and Slack fixes, but a complete fresh-login promotion/demotion journey, live Slack approval, native/iframe parity, and delegated-runtime caller-specific tool checks still require recorded acceptance. Merged code and healthy pods do not establish those results ([#2188](https://github.com/caipe-io/ai-platform-engineering/issues/2188), [#3222](https://github.com/caipe-io/ai-platform-engineering/issues/3222), [#3388](https://github.com/caipe-io/ai-platform-engineering/issues/3388)).
- **Next release**: direct A2A conversations and Agent Teams are tracked separately for 1.5.0 ([#3432](https://github.com/caipe-io/ai-platform-engineering/issues/3432)).

## Upgrade Guide: 1.3.6 → 1.4.0

### Scope and preparation

This guide uses the **published 1.4.0-rc.8 chart** as the candidate for 1.4.0.
Its chart and application versions are both `1.4.0-rc.8`. Recheck chart defaults
and image availability if the eventual stable tag differs from this candidate.
No deployment-specific values or private secret-store paths are assumed.

1. Back up application MongoDB data, authorization state, app catalogs, and runtime workspaces. Save the current chart revision, values, and explicit image pins.
2. Schedule a coordinated UI rollout for admin-grant ownership changes. Drain old UI replicas before resuming grant or login-reconciliation writes; old binaries do not understand pending ownership records.
3. For enabled remote profiles, upgrade UI, Engine, and matching workers together. Model connections also require compatible Dynamic Agents/Deep Agents and the credential-service endpoint.
4. Keep optional runtimes and bot transports disabled until their credentials, storage, network policy, and target-specific acceptance are ready.

#### Identity-provider audience override

A deployment that previously left this unset inherits the new bundled-Keycloak
audience. For a different issuer, keeping that inherited value can reject valid
bearer tokens. Supply the audience actually issued for this application.

**Before (1.3.6, no explicit override):**

```yaml
caipe-ui:
  config: {}
```

**After (external issuer example):**

```yaml
caipe-ui:
  config:
    OIDC_ACCEPTED_AUDIENCES: "https://api.example.test"
```

#### ExternalSecret API-version precedence

**Before (1.3.6 default):**

```yaml
global:
  externalSecrets:
    apiVersion: "v1beta1"
```

**After (rc.8 default):**

```yaml
global:
  externalSecrets:
    apiVersion: ""
```

The empty value honors the legacy LLM-secret setting before falling back to
`v1beta1`. If your installed CRDs require `v1`, set this field explicitly to
`"v1"`. Otherwise an inherited legacy setting can change which API is rendered.

#### Preserve an external-app catalog

Existing file and parent-directory mounts take precedence; the rc.6 empty-mount
regression is fixed. An installation-specific path workaround is no longer
required by that defect. Remove one only after rendering confirms a single
catalog at the intended path with all installations retained. The new optional
chart-managed reference looks like this:

```yaml
caipe-ui:
  agenticApps:
    existingConfigMap: example-app-catalog
    configMapKey: agentic-apps.yaml
  config:
    AGENTIC_APPS_INSTALL_ENABLED: "true"
    AGENTIC_APPS_CONFIG_PATH: "/etc/caipe-ui-agentic-apps/agentic-apps.yaml"
```

Supply the app-token signing secret through the existing deployment secret
mechanism. This release introduces no universal Vault path or automatic app-data
migration.

### Administrator-access migration

- Removing the OIDC admin group revokes recorded login-derived reasons on a new login or the existing refreshed-claim check, which runs on a four-hour interval. It is not immediate upstream logout or a sweep of inactive accounts.
- Preserve configured bootstrap admins and independently recorded manual grants. Do not infer direct-grant ownership from super-admin team membership alone.
- Audit **both** existing tuples and `admin_grant_ownership` rows, including rows whose tuple is absent. Historical CAS changes are not reconstructed automatically.
- Compare uncertain records with approved grant/revoke history. Reapply confirmed historical revocations through the fixed CAS path; remove old login-only grants explicitly when their provenance is established. Ambiguous legacy grants are retained for operator review.
- HTTP `503 AUTHZ_WRITE_PENDING` means an outcome requires verification, not that access is necessarily denied or rolled back. Do not automatically retry or clear `independent_pending` because the tuple appears absent.
- Before recovery, pause writers for the subject and drain outstanding requests. Reconcile approved reasons and exact tuples under the subject lock, clear the marker only after verification, then check effective access. Resolve pending records before rolling back to older binaries.

See [the ownership and recovery procedure](https://github.com/caipe-io/ai-platform-engineering/blob/1.4.0-rc.8/docs/docs/security/rbac/workflows.md#login--first-time-broker-login).

### Helm upgrade runbook

Use the existing release name, namespace, and reviewed values. These commands
stage **rc.8** for acceptance; they do not publish or deploy stable 1.4.0.
For GitOps-managed environments, make the equivalent chart/value change in the
owning repository and reconcile through its controller.

```bash
CHART=oci://ghcr.io/caipe-io/charts/ai-platform-engineering
RELEASE=example
NAMESPACE=example
helm get values "$RELEASE" -n "$NAMESPACE" -o yaml > values-before.yaml
helm get manifest "$RELEASE" -n "$NAMESPACE" > manifest-before.yaml
helm history "$RELEASE" -n "$NAMESPACE"
helm template "$RELEASE" "$CHART" --version 1.4.0-rc.8 \
  -n "$NAMESPACE" -f your-values.yaml > manifest-candidate.yaml
# Review images, catalog mounts, audiences, secrets, storage, and network policy.
helm upgrade "$RELEASE" "$CHART" --version 1.4.0-rc.8 \
  -n "$NAMESPACE" -f your-values.yaml --wait --timeout 15m
kubectl get deployments,statefulsets,pods -n "$NAMESPACE"
```

Check a fresh ordinary-user login, promotion and demotion, independently granted
admin access, revoked chat access, and permanent deletion. Exercise chat reload,
existing conversation history, app catalogs and native/iframe assistants, saved
model credentials, and every enabled runtime and bot approval flow. Record
blocked and untested paths separately from passing checks.

After stable artifacts are published and acceptance is approved, replace the
candidate version with `--version 1.4.0`, review the final chart/image diff, and
repeat the environment's normal deployment process.

### Docker Compose upgrade notes

The rc.8 source still defaults most application images to `1.3.6`, Engine to
`1.3.7-rc.7`, and the scheduler to `1.1.1`. Checking out the candidate alone does
not select rc.8 images. For candidate qualification, explicitly set and verify
every image family that you intend to upgrade, for example:

```dotenv
IMAGE_TAG=1.4.0-rc.8
HARNESS_ENGINE_IMAGE_TAG=1.4.0-rc.8
SCHEDULER_IMAGE_TAG=1.4.0-rc.8
```

Verify those manifests exist for the target architecture before pulling; retain
any intentional service-specific pins. Run `docker compose config --images`
and review the rendered configuration before `docker compose pull` and
`docker compose up -d`. Do not delete persistent volumes during an upgrade.
New `.env.example` defaults enable additional local features, including
workflows, autonomous agents, and the connected-credentials workspace; merge
only the settings intended for your installation rather than replacing a
working `.env`. Local-only credential-wrapping and localhost OAuth allowances
are not production settings.

Compose includes Engine with the Dynamic Agents profile and generates a private
UI/Engine token once in its persistent token volume when no private token is
supplied. Preserve that volume and coordinate both services during rotation.
This does not enable remote workers or move existing Deep Agents conversations.

### Rollback and deployment impact

- Restore the recorded chart/image configuration through the existing deployment controller; a Helm revision rollback does not restore MongoDB, OpenFGA, or workspace data.
- Before reverting authorization writers, resolve all pending ownership records and preserve the audited ownership state. Do not mix old and new ownership writers while mutations continue.
- Engine-bound conversations require their matching runtime and saved workspace/session state. Drain runs and follow the documented session-adoption procedure before changing routing; a browser refresh is not a migration.
- New managed Claude profiles require compatible workers. Model connections require coordinated UI/runtime support. Existing deployment-managed profiles and environment-managed models retain their compatibility paths.

Use the [runtime deployment guide](https://github.com/caipe-io/ai-platform-engineering/blob/1.4.0-rc.8/deploy/harness-engine/HELM.md),
[persistence guide](https://github.com/caipe-io/ai-platform-engineering/blob/1.4.0-rc.8/docs/docs/installation/persistence.md), and
[bot transport guide](https://github.com/caipe-io/ai-platform-engineering/blob/1.4.0-rc.8/docs/docs/integrations/bot-harness-gateway.md) for the options
enabled in your environment.
