## Highlights

CAIPE 1.3.1 restores compatibility for saved external MCP connections when an
application moves to an iframe runtime. With a compatible app release, users can
keep their saved connection URL and sign in again without recreating the
connection.

:::note Release preparation

## Bug Fixes

- **Saved MCP connections** — External clients can continue using their original
  connection URL after an app moves to an iframe runtime, including sign-in
  discovery and schema access. The app must also support the original connection
  identity ([#3129](https://github.com/caipe-io/ai-platform-engineering/pull/3129)).

## Breaking Changes

No breaking Helm configuration changes were found relative to 1.3.0. Existing
saved connections do not need a client configuration change or database migration.
Restoring sign-in compatibility requires a matching app update; upgrading CAIPE
alone is insufficient.

## Known Issues and Limitations

- Apps without support for the original connection identity can still fail
  sign-in discovery after the host upgrade. Deploy the matching app fix before
  asking users to reconnect.
- Revoked grants still require sign-in. Existing OAuth registrations and permitted
  resource URLs must be retained during the upgrade.
- Live deployment validation remains necessary for existing tokens, token refresh,
  and fresh sign-in; local compatibility tests do not verify deployment credentials.

## Upgrade Guide: 1.3.0 → 1.3.1

### Overview

This is a targeted host routing fix. There are no chart source changes between
1.3.0 and the release candidate, and no new required Helm values or secrets.
Deploy the host together with an app release that supports stable root MCP
resources. For TOME, that means a release containing
[the companion fix, #592](https://github.com/cisco-eti/tome/pull/592).
A merged app fix does not by itself establish that an installed image contains it.

### Helm Values Changes

- No keys were added, removed, renamed, or deprecated in the chart source.
- No chart defaults changed in the candidate.
- The published 1.3.0 parent-chart values match the candidate source values.
- The published 1.3.1 values and chart metadata cannot be verified until that
  artifact is available. Release automation supplies the chart and image versions.
- If your deployment explicitly pins the UI image tag or digest, update that pin
  to the published 1.3.1 image; changing the chart version alone will not replace
  an explicit image override.

### Upgrade Runbook

#### 1. Prepare the app and identity configuration

- Confirm the installed app declares its original root endpoint in `api.mcp.path`.
  CAIPE preserves this endpoint and its `openapi.json` schema through the app gateway.
- Deploy an app version that recognizes the host-controlled
  `x-caipe-mcp-resource-path` selector, advertises the selected OAuth resource and
  metadata URL, and validates tokens against that resource. Caller-supplied
  selector values are stripped by the host.
- Keep the OAuth issuer, client registrations, refresh grants, and authorization
  server's permitted resource URLs for both the original root endpoint and the
  hosted endpoint. Do not rewrite saved connections.
- If secondary OIDC is configured, retain both public URL keys in
  `CAIPE_SECONDARY_AUTH_RESOURCES`.
- Check configured app paths for collisions. A root MCP path must not overlap
  another app's MCP path or API mount; ambiguous ownership is rejected.

For example, a saved root URL can remain
`https://example.com/api/example/mcp` while the hosted URL is
`https://example.com/apps/example/api/example/mcp`. Both resource identities must
remain registered with the authorization server.

#### 2. Confirm the release artifacts and upgrade the host

Once 1.3.1 is published, review its chart metadata and values:

```bash
helm show chart oci://ghcr.io/caipe-io/charts/ai-platform-engineering --version 1.3.1
helm show values oci://ghcr.io/caipe-io/charts/ai-platform-engineering --version 1.3.1
```

Upgrade using your existing release name, namespace, and values:

```bash
helm upgrade example oci://ghcr.io/caipe-io/charts/ai-platform-engineering \
  --version 1.3.1 \
  --namespace example \
  -f your-values.yaml \
  --wait --timeout 10m
```

For GitOps installations, update the chart version and any explicit UI image pins
in the deployment repository, then let the deployment controller reconcile them.

#### 3. Verify saved and hosted connections

```bash
kubectl get pods -n example
```

- Use a client with an existing saved root URL: confirm discovery, initialization,
  and tool access without changing the saved URL.
- Verify an existing access token, a refresh grant, and a fresh sign-in against
  that same root URL. Sign in within the existing connection if a grant was revoked.
- Verify the hosted app URL continues to work with its own resource identity.
- Confirm disabled apps and invalid credentials remain denied.

See [the app compatibility requirements](https://github.com/caipe-io/ai-platform-engineering/blob/9f521e0c7/docs/docs/features/agentic-apps.md#preserve-saved-external-mcp-connections)
for the full rollout contract.

### Deployment Impact

Deployments without external MCP clients using saved root URLs require no
additional configuration for this fix. Deployments with those clients need the
matching app update and retained OAuth resource registrations described above.
No deployment-specific values file was supplied for this release review.
